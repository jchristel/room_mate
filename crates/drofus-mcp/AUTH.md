# Authentication: what is known, and what is still open

Every dRofus tool builds its request and hands it to the `Authenticator` in `src/auth.rs`. The scheme in use is
**`Authorization: Reference {key}`** (see "What a working client does" below); the browser OAuth flow the owner
prefers is **not built** and is blocked on dRofus (no OAuth endpoints are known). This file records what was found.

## What was observed (2026-10-30, against `https://api-no.drofus.com`)

- **The OpenAPI definition declares no security scheme.** `swagger.json` has no `securitySchemes`, no `security`
  and no `servers`; the only things under `components` are `schemas` and `parameters`. It cannot say how a request
  is signed.
- **An unauthenticated call is answered `401`, and the answer advertises three schemes.** `GET /api/x/y/rooms` with
  no credential returns an empty body and three `WWW-Authenticate` headers:
  - `Basic realm="Use Basic authentication scheme defined in RFC 7617 to submit reference token; use token as password"`
  - `Bearer`
  - `Reference`

  Read literally: a *reference token* (an opaque token, not a self-contained JWT) can be sent as the **password of
  HTTP Basic**, and `Bearer` is also offered. What the user name should be, and where the token comes from, are
  not stated. This is the server's own hint, not a tested recipe: **no credentialed call has been made.**
- **The Swagger page does not configure OAuth.** Its `index.js` sets `supportedSubmitMethods: []` and
  `tryItOutEnabled: false` (the page documents, it does not call) and passes an *empty* OAuth object to
  `initOAuth` (no client id, no scopes, no authorize or token URL). The page's own Login button is therefore not
  Swagger UI's standard Authorize dialog; where it goes is **not visible from the static files**.
- **Guessed identity endpoints do not exist:** `/.well-known/openid-configuration`, `/login`, `/api/login` and
  `/connect/token` all return 404 on the API host. `/swagger/oauth2-redirect.html` is Swagger UI's stock redirect
  page and says nothing about dRofus.
- The brief says Login leads to an interactive sign-in (user name and password, or Microsoft single sign-on).
  **That was not observed here**: the Login button is created by JavaScript and Playwright was not installed on
  this machine, so the page was read from its files and not rendered.

## What a working client does: duHast PushIt (C#), read 2026-10-30

`SampleCodeRevitBatchProcessor/VS/duHastRevitApplications/PushIt` (`DrofusDataSource.cs`, `DrofusAuthSettings.cs`,
`DrofusAuthToken.cs`) already talks to this API from Revit. It is the best evidence there is:

- **Header: `Authorization: Reference {key}`**, plus `Accept: application/json`. That is the third scheme the 401
  advertises, so `Reference` (not Basic, not Bearer) is the one a real client uses.
- **The key is an API key generated by the user in dRofus's "Power Query credentials dialog"** (its own wording).
  It is per user and project-scoped: PushIt's messages say a 401 is "Invalid API token" and a 403 is "Token has no
  access to this project". PushIt calls this mode read-only, "suitable for PoC and dashboards".
- **The OAuth2 fields in PushIt are stubs.** It carries `OAuthClientId`, redirect URI, authorization and token
  endpoints, scopes (`openid profile`) and a loopback callback port, all marked "future", "obtained from drofus
  after manual registration". So the browser flow is not available without registering a client with dRofus
  support; nobody has the endpoints.
- **Hosts are regional**: `https://api-{no|eu|us|ca|au}.drofus.com`. Every path is `/api/{database}/{project}/...`,
  which the PushIt settings call database id and project number (e.g. `01`).
- Its connection test is `GET .../rooms`; it pages with `$top`/`$skip` (500 per call) and reads
  `OPTIONS .../rooms` and `GET .../attributeconfigurations` for field metadata.

**Implemented: `auth::ReferenceKey`**, `Authorization: Reference {key}`, the key from `DROFUS_API_KEY` (or
`--api-key`) as a `Secret`. The header is marked sensitive so a debug-printed request hides it, a key that cannot
be a header value is refused without echoing it, and a key is never attached to plain `http` off this machine
(loopback is allowed for a tunnel or a mock). With no key, `Unauthenticated` refuses every call before any request
and says what to set. **Untested against the live service from this crate**: no credentialed call has been made
here; the scheme is PushIt's.

## What is not known

- Whether the API key can be generated for a service account, or only per person (PushIt's key comes from a user's
  dialog).
- Whether Basic-with-token and Bearer are equivalent to `Reference` at all; PushIt only uses `Reference`.
- Token lifetime, and whether anything has to be refreshed.
- Whether a regional host other than `api-no.drofus.com` is needed for the project (the base address is
  configuration: `--base-url` / `DROFUS_BASE_URL`).
- Whether the credential is per user (so reads are filtered by that user's rights, as the `OPTIONS` metadata
  endpoints suggest: "available properties to select *for current user*") or per integration.

## Where the decision lands in the code

1. Write a type implementing `Authenticator` (`src/auth.rs`). It receives the `reqwest::RequestBuilder` and returns
   it with the header or cookie added; it may be asynchronous, for a token that has to be fetched.
2. Keep its credentials as `config::Secret`s.
3. Return it from `auth::for_config`, the one place the choice is made (or pass it to
   `DrofusMcp::with_authenticator`).
4. Keep the rule that an error from it never contains a credential: the client forwards the text to the model.
5. The tests already stamp a fake secret through a test authenticator and assert it never appears in an error or an
   answer (`client::tests`); extend those rather than writing new ones.
