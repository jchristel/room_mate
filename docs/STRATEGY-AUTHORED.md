# RoomMate — User-Authored Data & Documents Strategy

**Status: design settled, not built.** Nothing in this document ships today.
It records the shape agreed for storing data the *user* authors — manual room
connections, uploaded PDFs, their extracted text, and the scopes that bind
them to the room hierarchy — so the first implementation doesn't re-derive it.

Everything here is an application of rules the pipeline already follows
elsewhere; where a decision is genuinely new it is called out as such. The
existing docs it leans on: [Index](STRATEGY.md) (the upload envelope),
[Server](STRATEGY-SERVER.md) (`SnapshotStore`, manifest, milestones),
[Sources](STRATEGY-SOURCES.md) (the reference-source upload precedent),
[Browser](STRATEGY-BROWSER.md), [MCP](STRATEGY-MCP.md),
[Security](STRATEGY-SECURITY.md) (the trust boundary this data crosses once
authored content is user-submitted, not just machine-pushed).

## The problem this answers

Every data source so far is *machine-produced and re-derivable*: a Revit push
can be re-pushed, a reference CSV re-exported. User-authored data is neither.
Someone manually connecting a bay to a corridor — a link no geometry implies —
has produced information that exists nowhere else and cannot be regenerated by
re-running anything. Documents are the same: a fire strategy PDF is authored
elsewhere but is, from this system's point of view, unreproducible input.

That difference drives two questions, and the answers below generalize to every
user-authored kind that follows.

## Decision 1: user input is not gated on milestones

The tempting move — only accept user input against a milestone, so the data
can't drift out of sync with the model it describes — is wrong, and wrong for a
reason the existing architecture already states.

**Milestones are read-time pins over immutable snapshots.** That is why their
definitions live in the *settings bundle*, not storage (see
[Server](STRATEGY-SERVER.md)): they are user-authored per-project metadata that
selects among stored data, never data themselves. Routing authored input
through them would conflate two different things — "what the model said on
date X" and "what the user decided" — and would make every edit require
choosing a milestone first, which is a bad interaction and a worse data model.

**Instead: accept input always, pin it at read time like everything else.**
Each user-authored kind becomes its own snapshotted stream under the existing
store, and a milestone gains an optional pin for it, structurally identical to
the `reference_snapshots` pins that already exist:

- Input is accepted whenever the user makes it. No gate.
- A milestone view substitutes the pinned version during response assembly,
  *before* dedup / building filter / reference join / classification — the same
  substitution point milestone room snapshots already use, so every downstream
  step composes unchanged.
- A milestone that pins nothing for a kind joins the current one. Absent pin =
  live data, exactly as an absent `reference_snapshots` entry means "join that
  source's current data".

Sync-safety without blocking edits, and milestone views stay reproducible.

**The read-time reconciliation stance carries over unchanged.** An authored
reference to a room that no longer exists is a **skip + warn**, not an error —
the same signal-not-error discipline as an unmatched reference link key or a pin
to a since-deleted snapshot. Authored data outliving the geometry it references
is normal, not corruption.

## Decision 2: one store, extended — not a second backend

All user-authored kinds go into the existing `SnapshotStore` behind the trait,
alongside rooms and the reference sources:

```
<root>/<project>/<model>/<taken_at>.json          rooms          (exists)
<root>/<project>/reference/<src>/<taken_at>.csv   reference      (exists)
<root>/<project>/connections/<taken_at>.json      connections    (new)
<root>/<project>/documents/…                      documents      (new, see below)
```

Each new kind directory is a **reserved name `list_models` skips**, exactly as
`reference/` already is — otherwise it surfaces as a phantom model. Each is
indexed on the project manifest with the same filesystem-wins reconciliation
model snapshots use, and each rides `?taken_at=` through the same
`ensure_taken_at` / `validate_snapshot_id` pair (see [Index](STRATEGY.md), "The
upload envelope"). Adding a kind should be a manifest field and a reserved
name, not an architecture.

**Why one store rather than a database per kind:** a single manifest means one
reconciliation rule, one atomic-install path, one hot-reload, one `SAVE_LOCK`.
Separate backends would need a cross-store consistency story that buys nothing
here — and the trait already leaves a DB backend open as a *whole-store*
swap, which is the version of that idea worth keeping.

**The linking key is what it already is everywhere:** `project id` + `room id`,
with `taken_at` as the version axis. Nothing new is needed to join these.

## Connections (manual room adjacency)

Stored as **edges, not room mutations** — `{ from_room_id, to_room_id, kind,
note }`. Rooms stay raw in the snapshot; the join happens at response assembly.
Identical discipline to a reference source (stored raw, joined as its own
sub-object)
and for the same reason: a stored snapshot must remain exactly what was pushed.

**The one genuinely open question — durable vs per-snapshot.** Are connections
re-authored when the geometry changes, or do they survive model pushes?

Durable is almost certainly right for manually drawn bay↔corridor links:
nobody will redraw them on every Revit push, and re-authoring is precisely the
cost the feature exists to avoid. That makes connections **a single mutable
document with an append-only history** — snapshots exist for milestone pinning
and audit, not for correctness — with orphan-checking at read time (skip+warn,
per above). This is the position to build against unless something contradicts
it in use.

## Documents (PDFs)

Same principle, with one structural difference that matters: rooms and reference
CSVs
are *one blob per timestamp*; a document set is *many files, each with its own
revision history*. Re-uploading a whole set to change one PDF is wasteful and,
worse, loses identity — "the fire strategy" should stay the same document
across revisions, not become an unrelated file in a new folder.

**So identity and version split:**

```
<root>/<project>/documents/<doc_id>/<taken_at>.pdf         source, immutable
<root>/<project>/documents/<doc_id>/<taken_at>/p0001.txt   derived text, per page
<root>/<project>/documents/<doc_id>/<taken_at>.meta.json   page count, extractor version
<root>/<project>/documents/index/<taken_at>.json           identity, scopes
<root>/<project>/documents/.index/                         search index (disposable)
```

`doc_id` is the stable key (slug or UUID); `taken_at` is the version axis, as
everywhere else. A milestone's document pin is therefore **not** a single
snapshot id but a map, `doc_id → taken_at` — structurally the same shape as
`Milestone::attachments` (model id → snapshot `taken_at`). That the existing
milestone type already expresses this shape is a good sign the decomposition is
right.

**Ingest.** Raw body upload, `POST /projects/{id}/documents/{doc_id}`,
following the reference upload's raw-`text/csv` precedent — no multipart
dependency — with
an explicit `DefaultBodyLimit` (axum's silent default is 2 MB; PDFs need far
more). The **validate-before-store** rule holds, but "valid" for a PDF is
thinner than for a CSV: magic bytes, size, parseability. There is no label set
to check against settings, so ingest validation is genuinely shallow, and that
is fine — it must simply not be *skipped*.

### Extracted text is derived data

Text extraction is worth doing at ingest — cheap with `lopdf`, and it is what
makes search possible later — but it is **derived, not source**, and that
governs where it lives:

- **Beside the PDF, under the same version key.** Milestone pinning then
  composes for free (a pin is already `doc_id → taken_at`; text resolves by the
  same key, with no second lookup and no way to pin a PDF to one version and
  its text to another). Deletion is one operation — removing a version removes
  its derivatives, rather than creating a second reconciliation rule and a new
  class of orphan. And the manifest stays a manifest: identity and references,
  not megabytes of payload.
- **Record the extractor version** in the meta file. Extraction is lossy and
  library-dependent; when `lopdf` is upgraded or OCR is added, you need to know
  which text came from which extractor to decide what to re-derive. Without it,
  re-extraction is all-or-nothing.
- **Regeneration is safe and explicit.** Derived files are rebuildable from
  source, so a missing `.txt` is skip+warn plus a re-derive, not an error.
  That also means extraction may be **deferred**: ingest validates and stores
  the PDF synchronously, derives text after, and the document is usable (just
  not searchable) in between.

### One file per page, not byte offsets

A search hit must name a location — `(project, doc_id, taken_at, page)`. A hit
that points at a 200-page fire strategy without naming the page is useless.
Extraction flattens a PDF into one continuous string and page boundaries
vanish, so page identity has to be captured *during* extraction, when the
library still knows which text came from which page.

Two ways to keep it: per-page byte ranges in the meta file, or one `.txt` file
per page. **Choose one file per page.** Page identity is the filename, there is
no offset arithmetic, a page is the natural retrieval unit for an index anyway,
and the MCP page-fetch tool becomes a direct file read with no seek logic. The
cost is many small files per document, which is acceptable.

**This is the one thing that is expensive to backfill.** Everything else in
this document is additive; page identity is not. Once a flat `.txt` has been
written, the mapping is gone and recovering it means re-extracting the entire
corpus. Do it before a corpus exists.

## Scoping documents to the hierarchy

A document is associated with **any level of the room hierarchy**, not only a
room. Since the hierarchy is already configurable per project (`[[hierarchy]]`
in settings), an association is a **scope expression against it** — a partial
hierarchy path, where partial means "everything below":

```json
{
  "doc_id": "fire-strategy",
  "scopes": [
    { "path": { "Building": "Block A", "Level": "L03" } },
    { "path": { "Building": "Block B" } }
  ]
}
```

`{}` is project-wide; a full path is a single room. **One shape covers every
depth** — no separate `room_ids` / `level_ids` / `building_ids` fields — and it
survives a room being renumbered as long as it stays in the same level, which
a room-id list would not.

**The association lives in the document index, never in the room snapshot.**
Rooms stay raw; the join happens at response assembly. Same discipline as
reference sources and connections.

**Two entry points, one contract.** `PUT
/projects/{id}/documents/{doc_id}/scopes` is the contract; the settings-page
UI (drag a document onto a hierarchy tree node) is a client of it, not a
parallel path. **Replace-whole-list, not patch** — mirrors how settings saves
work, avoids defining merge semantics, and runs under the same `SAVE_LOCK` as
settings saves and reference uploads so a scope edit can never race one. Upload may
carry scopes in the same call; the UI simply PUTs after the drop.

**Validate the field, warn on the value.** A scope naming a hierarchy *field*
the project doesn't declare is a **save-time error** — settings knows the field
list, so this is startup-loud validation of the kind settings already does. A
scope naming a *value* that currently matches nothing (`Level: "L09"` in a
model with three levels) is **skip + warn at read**, since the model may simply
not have been pushed yet. This is the same split the codebase already makes
between what settings can validate and what only the data can answer.

**Read side.** `/rooms` gains a `documents` sub-object per room: every document
whose scope path is a prefix of that room's classification path. Cheap —
index the scopes once per request into a map keyed by path prefix, then each
room is a few lookups up its own ancestry. Derived at response assembly, never
stored, like the reference join and `classification`.

**Open decision: are scopes pinned by milestones?** Scopes live in the index,
which is mutable, so as sketched a milestone pin captures document *versions*
but not *scopes*. If scopes should be pinned too, the index needs the same
`taken_at` versioning as the documents themselves — hence
`documents/index/<taken_at>.json` above rather than a single flat
`index.json`. The versioned form is written into the layout because it is
cheap now and awkward later; whether milestones actually pin it can be decided
when there is a reason to.

## Text search (deferred, but the layout is built for it)

Not to be built now. It is described here because three properties of the
layout above are what make it cheap later, and all three are expensive to
retrofit.

1. **Stable addressing.** `(project, doc_id, taken_at, page)` names a hit.
   One-file-per-page is what supplies the page component. (See above — the one
   thing that must be done up front.)
2. **The index is a projection, never a source.** Built from the `.txt` files,
   rebuildable from scratch, carrying a version stamp like the extractor
   version. A schema change, a tokenizer change, or a corrupt index is then a
   rebuild, not a data loss. It lives at `documents/.index/` — dotted so
   `list_models` skips it, and safe to delete at any time. Keeping the text on
   disk is precisely what makes the index disposable.
3. **Milestone scoping is a filter, not a separate index.** Index every
   version with `taken_at` as a filterable field; a milestone query filters to
   its pinned versions. One index serves the latest view and every milestone
   view. An index per milestone would multiply storage and break the moment
   someone edits a pin.

**Implementation, when it happens:** Tantivy — pure Rust, embedded, no service
to run, and its schema model handles the filter fields cleanly. Put the writer
behind a `DocumentIndex` trait the way `SnapshotStore` is a trait, so a
test double and the real thing swap the same way `MemStore`/`FsStore` do.

## MCP surface

Documents are where MCP pays off most, and the tools fall out of the layout
without any new concepts:

- `search_documents(project, query, milestone?)` → `(doc_id, page, snippet,
  score)`. Search narrows.
- `get_document_page(project, doc_id, taken_at, page)` → text. Fetch reads.
- `list_documents(project, scope?)` → identity plus scopes, alongside the
  existing `list_milestones`.

The two-step (search narrows, fetch reads) is the shape a model actually wants,
and it is only expressible because pages are addressable.

Note that all three are **read-only**, which keeps them inside the existing MCP
boundary — the MCP server deliberately exposes no ingest (see
[MCP](STRATEGY-MCP.md)), and nothing here asks for an exception. Document
*upload* and scope edits stay HTTP-only.

## Deferred

Design settled above, not built: connections storage and the connections edge
model; document ingest, storage, and per-page extraction; hierarchy scopes and
the `documents` sub-object on `/rooms`; milestone pins for connections and
documents; the settings-page UI for both; text search and its index; the
`DocumentIndex` trait.

Genuinely undecided, flagged in place: whether connections are durable or
per-snapshot (durable recommended), and whether milestones pin document scopes
as well as document versions (the versioned index layout keeps the option
open).

**Considered and rejected: bulk FF&E manual pairing as a user-authored kind.**
When the model and the reference source each report N of the same item type in a
room, there
is generally no key distinguishing which is which, and manual pairing was
considered as the resolution. Rejected on **volume** — the item counts make
hand-pairing infeasible, so reconciliation is reported as *count buckets per
`(room, type)`*, derived fresh at response assembly and never stored (see
[Sources](STRATEGY-SOURCES.md)). FF&E buckets therefore sit with
`classification` and the reference join, not with the authored kinds here.
**The narrow exception is a required future feature, not a reopening of this
decision:** a minority of high-value items — major equipment, anything with a
commissioning trail — will need an asserted correspondence between one model
instance and one reference item. Such an assertion *is* user-authored data,
unreproducible by re-running either export, and when built it follows the
connections model above. It is additive: the bucket stays the primitive and the
keyed match tier simply gains entries.
